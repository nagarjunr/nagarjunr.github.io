Give AI a job before you give it a model.

By Nagarjun Rajendran / 22 November 2026

“Let us add an AI assistant” is an implementation idea. It still needs a problem worth solving.

In an IoT setting, there are plenty of things an assistant could say. It could summarize telemetry, explain an anomaly, or suggest an investigation. The useful question is which of those helps someone make a better decision.

Name the person and the next action.

Consider an energy optimization advisor built around simulated devices. A focused job might be: help a facilities operator identify which unusual consumption pattern deserves investigation first.

That gives the prototype a practical boundary. It needs evidence about the pattern, enough context to explain why it matters, and a clear way for the operator to check the explanation.

Separate evidence from interpretation.

Measured consumption, device status, and calculated comparisons should have a traceable source. An AI explanation can help someone understand those facts, but the wording should make assumptions visible.

I would ask a prototype to distinguish three things:

  • Observed: what the available readings show, with the relevant time period.
  • Inferred: a possible explanation, with the assumptions behind it.
  • To verify: the next check a person could make before acting.

Decide how to judge usefulness.

Before tuning a prompt, define a few representative situations. Include normal operation, incomplete data, and a case where the evidence does not support a recommendation.

Then compare the assistant with the existing workflow. Does it help the operator find the issue sooner? Does it point to the right evidence? Does it acknowledge when more information is needed?

A useful AI prototype has a clear job, a source of evidence, and a way to tell whether it helped.

The model matters. But those decisions make the model choice a more grounded conversation.

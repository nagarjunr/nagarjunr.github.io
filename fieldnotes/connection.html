Design for the day the connection fails.

By Nagarjun Rajendran / 22 November 2026

A sensor sends a reading. A gateway forwards it. A dashboard updates. The demo works. Now disconnect the gateway.

That small test opens a much more useful architecture conversation. What gets lost? What waits? And what does the person looking at the dashboard believe is happening?

Start with the consequence.

Before choosing a message broker or a database, ask what a missing reading means. An hourly environmental trend and a time-sensitive equipment alert need different treatment. The consequence of delay should shape the design.

For a simulated energy monitoring system, I would begin with three questions:

  • Can the device keep collecting readings while the network is unavailable?
  • How long can it store them, and what happens when that space runs out?
  • How will the user distinguish a quiet building from a disconnected sensor?

Recovery is part of the design.

Restoring the connection is only the beginning. Buffered readings can arrive late or more than once. A useful event needs enough context to explain where it came from and when the measurement happened.

The receiving system needs a deliberate policy for duplicates, old readings, and gaps. Those choices should follow the business question. A historical energy report and a live operational view may handle the same late event differently.

Make uncertainty visible.

A dashboard that shows the last reading without its age can look healthy while the system is disconnected. Show when data was measured, when it was received, and whether the source is still communicating.

The failure path is part of the user experience.

My preferred starting point is simple: disconnect a device during a prototype, reconnect it, and trace what happens to one reading. That exercise often reveals more than another box on the architecture diagram.

Connected systems. Clear thinking.
